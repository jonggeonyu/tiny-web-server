# SPEC.md · Reverse Proxy 데모 명세

이 문서는 구현에 필요한 결정 사항을 모두 담고 있습니다. 숫자 값은 이 문서의 값을 그대로 씁니다.
화면 모양과 애니메이션은 `docs/prototype.html`을 따릅니다. 단, prototype 안의 **가짜 서버 흉내 코드는 참고용**이며, 실제 데모 페이지는 C 서버가 보내는 데이터로 그립니다.

---

## 1. 목표와 범위

- tiny-server(CS:APP)를 바탕으로 **C로 Reverse Proxy와 백엔드 서버를 직접 구현**합니다.
- 블랙 프라이데이 시나리오로 다음 네 가지를 데모 웹 페이지에서 보여줍니다.
  1. 서버 1대 직결 시 과부하 다운 (Proxy 끄기)
  2. 경로 기반 라우팅 + 그룹별 Round-Robin
  3. 캐싱으로 인한 부하 감소
  4. 장애 처리: 응답 멈춤(504, 재시도), 이상 응답(502), 헬스 체크 제외·복귀
- 발표는 5분이며 `README.md`를 띄워 진행하고, 데모 페이지는 브라우저에서 보여줍니다.
- 발표 중 조작은 모두 **데모 페이지 UI**로 합니다. 터미널은 서버를 시작하고 끄는 데만 씁니다.

---

## 2. 전체 구성

```
 [브라우저 데모 페이지]
        │  GET /static/demo.html, GET /api/events (SSE), POST /api/control/*
        ▼
 ┌──────────────── proxy 프로세스 (:8080) ────────────────┐
 │  Reverse Proxy 데이터 경로   │  데모 제어부              │
 │  - 정적 파일 서빙           │  - 트래픽 생성기(loadgen)   │
 │  - 라우팅 + Round-Robin     │  - 제어 API                │
 │  - 캐시                     │  - 이벤트 허브(SSE)         │
 │  - 타임아웃·재시도·헬스 체크 │                            │
 └──────────────────────────────────────────────────────┘
        │ /products/*                 │ /orders/*
        ▼                             ▼
 상품 서버 1·2·3 (:8001~8003)    주문 서버 1·2 (:8011~8012)
 (같은 backend 프로그램을 포트·이름만 바꿔 5개 실행)
```

| 프로그램 | 포트 | 이름(id) | 그룹 |
|---|---|---|---|
| proxy | 8080 | - | - |
| backend | 8001 | products-1 | products |
| backend | 8002 | products-2 | products |
| backend | 8003 | products-3 | products |
| backend | 8011 | orders-1 | orders |
| backend | 8012 | orders-2 | orders |

**트래픽 생성기는 proxy 프로세스 안의 별도 모듈**입니다. 브라우저는 한 서버에 동시 연결을 6개 정도밖에 열지 못해 폭주를 만들 수 없기 때문입니다. 트래픽 생성기는 Proxy 데이터 경로와 코드를 분리하고, Proxy에 요청할 때도 일반 클라이언트처럼 `127.0.0.1:8080`에 TCP로 접속합니다.

## 3. 요청 종류와 트래픽

| 종류(kind) | 요청 | 비율 | 경로 그룹 | 캐싱 |
|---|---|---|---|---|
| detail | `GET /products/{id}` | 45% | products | 함 (TTL 10초) |
| stock | `GET /products/{id}/stock` | 30% | products | 안 함 (실시간 정보) |
| order | `POST /orders` (작은 JSON 본문) | 25% | orders | 안 함 |

- `{id}`는 1, 2, 3 중 무작위(인기 상품 3개).
- 도착 간격은 **무작위(지수 분포, 포아송 도착)**. 같은 간격으로 보내지 않습니다.
- 트래픽 양: 세일 전 초당 1건, 세일 중에는 슬라이더 값(초당 0~100건).

## 4. 백엔드 서버 (`backend`)

tiny.c를 바탕으로 만듭니다. 실행: `./backend -p 8001 -n products-1 -g products`

### 4.1 엔드포인트

| 요청 | 응답 (200, `Content-Type: application/json`) |
|---|---|
| `GET /products/{id}` | `{"id":1,"name":"상품 1","price":19900,"server":"products-1"}` |
| `GET /products/{id}/stock` | `{"id":1,"stock":42,"server":"products-1"}` (stock은 매번 바뀌는 값) |
| `POST /orders` | `{"order_id":123,"server":"orders-1"}` (본문은 Content-Length만큼 읽고 버림) |
| `GET /health` | `200 OK`, 본문 `ok`. **처리 한계·대기열과 무관하게 즉시 응답** (단, 아래 장애 모드 영향은 받음) |
| `GET /__admin/stats` | `{"id":"products-1","mode":"normal","active":3,"queue":0,"overloaded":false,"done":120}` |
| `POST /__admin/mode?value=normal\|hang\|bad` | 모드 변경 후 `200 OK` |
| `POST /__admin/reset` | `done`을 0, 모드를 normal, `overloaded`를 false로 되돌린 뒤 `200 OK`, 본문 `ok` |
| 그 밖의 경로 | 404 |

- 모든 응답에 `Connection: close`, `Content-Length`를 붙입니다.
- `/__admin/*`은 **장애 모드와 상관없이 항상 즉시 응답**합니다(조작이 막히면 안 되므로).

### 4.2 처리 시간과 처리 한계

| 항목 | 값 |
|---|---|
| 요청당 처리 시간 | 300ms (`/products/*`, `/orders` 모두. `usleep`으로 흉내) |
| 동시 처리 한계 | 8건 (세마포어 또는 뮤텍스+조건변수) |
| 대기 | 한계를 넘은 요청은 기다림. 기다리는 수를 `queue`로 셈 |
| 과부하 | `queue`가 50을 넘으면 `overloaded = true`. 이 동안 새 요청에는 즉시 `503` |
| 회복 | `queue == 0`이고 `active < 3`이 되면 `overloaded = false` |

숫자 확인: 트래픽 100건/초에서 상품 서버 1대는 조회 25건/초 × 0.3초 = 동시 7.5건(한계 8건의 약 94%)으로, 게이지가 빨갛게 차지만 다운되지는 않습니다. 캐시를 켜면 재고 조회만 와서 동시 약 3건(약 38%)이 됩니다. Proxy를 끄면 1대가 100건/초를 모두 받아 금방 과부하가 됩니다.
또 캐시를 끈 채 100건/초에서 상품 서버 1대가 빠지면 남은 2대가 각각 동시 약 11건(한계 8건 초과)을 받아 과부하가 되므로, 데모 장면 3(서버 멈춤)은 **캐시를 켠 상태 그대로** 진행합니다.

### 4.3 장애 모드

| 모드 | 동작 | Proxy 입장 |
|---|---|---|
| normal | 정상 처리 | - |
| hang | 요청을 끝까지 읽은 뒤 **응답하지 않고 기다림**. 모드가 hang이 아니게 되는 순간 기다림을 끝내고 **바뀐 모드대로 처리**: normal(`/__admin/reset` 포함)이면 정상 처리(동시 8건·대기열·300ms 규칙 그대로) 후 응답, bad면 `THIS IS NOT HTTP`. 30초가 지나도 hang이면 응답 없이 연결을 닫음. `/health`도 같음 | 응답 타임아웃 |
| bad | 요청을 읽은 뒤 HTTP 형식이 아닌 바이트(`THIS IS NOT HTTP\r\n\r\n`)를 보내고 닫음. `/health`도 같음 | 잘못된 응답 |

### 4.4 동시성

연결마다 스레드 하나(detached `pthread`). tiny는 한 번에 한 요청만 처리하므로 이 부분을 바꿉니다.

### 4.5 구현하며 정한 사항

1단계를 구현하며 SPEC에 없던 부분을 아래처럼 정했습니다.

| 항목 | 결정 |
|---|---|
| 장애 모드와 처리 자리 | hang·bad 요청은 처리 자리를 차지하지 않음(`active`·`queue`에 세지 않음). prototype과 같음 |
| 장애 모드 적용 범위 | `/__admin/` 밖의 모든 경로(없는 경로 포함) |
| hang 대기 끝 | 모드가 hang이 아니게 되면 바로 끝내고 바뀐 모드대로 처리(4.3). 30초가 지나면 응답 없이 닫음 (6단계 뒤 변경: 처음에는 normal일 때만 끝내고 응답 없이 닫았음) |
| 과부하 중 대기 요청 | 이미 줄을 선 요청은 끝까지 처리 (prototype은 대기열을 503으로 비우지만 SPEC을 따름) |
| 메서드가 틀릴 때 | 아는 경로에 다른 메서드면 `405` |
| 에러 본문 | `{"error":"Not Found","server":"products-1"}` 형식 |
| 가격 · 재고 | 가격 `9900 + id×10000`(상품 1 = 19900), 재고 0~99 난수 |
| `/__admin/mode` 응답 본문 | `ok` |
| 상태 줄 | tiny처럼 `HTTP/1.0` |
| 요청 없는 연결 | 10초 동안 요청이 오지 않으면 끊음 |
| 스레드 스택 | 256KB (hang 중 스레드가 많이 쌓일 때 대비) |
| 대기 순서 | 도착 순서가 보장되지 않음(조건변수 방식). 데모에는 영향 없음 |
| hang에서 풀린 요청 | 처리하기 전에 상대(Proxy)가 이미 연결을 닫았는지 `recv(MSG_PEEK\|MSG_DONTWAIT)`로 확인. 닫혔으면 처리하지 않고 정리만 함(이미 포기된 요청이 처리 자리를 한꺼번에 차지하지 않게) |
| reset과 `done` | `/__admin/reset` 전에 도착한 요청(처리 중·대기 중)은 나중에 끝나도 `done`에 세지 않음. reset 직후 화면이 0에서 시작하도록 (6단계에서 추가) |

## 5. Reverse Proxy (`proxy`)

tiny.c를 바탕으로 만듭니다. 실행: `./proxy -c proxy.conf`

### 5.1 설정 파일 (`proxy.conf`)

```conf
listen      8080
static_root ./static

# route <경로 접두사> <그룹 이름> <서버 id>=<주소:포트> ...
route /products/  products  products-1=127.0.0.1:8001 products-2=127.0.0.1:8002 products-3=127.0.0.1:8003
route /orders     orders    orders-1=127.0.0.1:8011 orders-2=127.0.0.1:8012

connect_timeout_ms   1000
read_timeout_ms      3000
health_interval_ms   2000
health_timeout_ms    1000
health_fail_limit    2
cache_ttl_ms         10000
```

- `#`으로 시작하는 줄과 빈 줄은 무시합니다.
- 설정 파일이 없거나 형식이 틀리면 어느 줄이 왜 틀렸는지 출력하고 종료합니다.
- `route /orders`는 `/orders`와 `/orders/...`를 모두 받습니다.

### 5.2 정적 파일 서빙

| 요청 | 처리 |
|---|---|
| `GET /` | `302`로 `/static/demo.html`에 이동 |
| `GET /static/*` | `static_root` 아래 파일을 읽어 응답. 백엔드로 보내지 않음 |
| MIME | html, css, js, json, png, jpg, gif, svg, ico. 그 밖은 `application/octet-stream` |
| 없는 파일 | 404 |
| `..`이 들어간 경로, 루트 밖 접근 | 403 |

### 5.3 라우팅 + Round-Robin

- 요청 경로를 `route` 규칙의 접두사와 비교해 그룹을 정합니다. 맞는 규칙이 없으면 404.
- 그룹마다 Round-Robin 카운터를 따로 둡니다. **헬스 체크로 제외된 서버는 순서에서 건너뜁니다.**
- 그룹의 서버가 모두 제외되면 `503 Service Unavailable`.

### 5.4 요청 전달과 응답 헤더

- 클라이언트 요청을 백엔드로 그대로 보내되, `Connection: close`로 바꾸고 `X-Forwarded-For: <클라이언트 IP>`를 붙입니다. POST 본문은 `Content-Length`만큼 함께 보냅니다.
- 백엔드 응답은 끝(EOF)까지 읽은 뒤, 상태 줄이 `HTTP/1.x NNN`이 아니면 **잘못된 응답**으로 봅니다.
- 클라이언트에게 돌려주는 응답에 아래 헤더를 붙입니다. 트래픽 생성기가 이 헤더로 이벤트를 만듭니다.

| 헤더 | 예 | 의미 |
|---|---|---|
| `X-Route` | `products` | 라우팅된 그룹 (`static`이면 정적) |
| `X-Upstream` | `products-3` | 최종으로 응답한 서버 (캐시 HIT면 `-`) |
| `X-Tries` | `products-2:timeout,products-3:ok` | 시도한 서버와 결과를 순서대로 |
| `X-Cache` | `HIT` / `MISS` / `BYPASS` | 캐시 결과 (캐시 대상이 아니거나 캐시가 꺼져 있으면 `BYPASS`) |

`X-Tries` 결과 값: `ok`, `timeout`, `connect_fail`, `no_response`, `bad_response`.

| 결과 | 뜻 |
|---|---|
| `ok` | HTTP 응답을 받음 (상태 코드와 상관없이, 백엔드의 503도 `ok`) |
| `connect_fail` | 연결하지 못함, 또는 요청을 다 보내지 못함 (요청이 서버에 닿지 않음) |
| `timeout` | 요청을 다 보낸 뒤 3초 안에 응답을 다 받지 못함 |
| `no_response` | 요청을 다 보낸 뒤 **한 바이트도 받지 못하고** 연결이 닫히거나 끊김 (EOF, ECONNRESET). 서버가 죽었거나 응답 없이 닫은 경우 |
| `bad_response` | 응답을 받았지만 상태 줄이 HTTP 형식이 아님, 또는 일부만 받고 끊김, 2MB 초과 |

- Proxy가 직접 만드는 에러 응답(502·503·504)의 본문은 `{"error":"Gateway Timeout"}`처럼 짧은 JSON입니다.

### 5.5 캐시

| 항목 | 값 |
|---|---|
| 대상 | `GET /products/{숫자}` 와 정확히 일치하는 경로만 (재고 `/stock`은 제외) |
| 저장 | 백엔드가 200으로 응답했을 때만, 응답 전체(헤더+본문)를 경로를 키로 저장 |
| TTL | 10초. 지나면 Miss로 처리하고 다시 받아옴 |
| 켜기·끄기 | 제어 API로 바꿈. **끄면 저장된 내용을 모두 비움.** 시작 상태는 꺼짐 |
| 동시 접근 | 뮤텍스로 보호 |

### 5.6 장애 처리 규칙

| 상황 | 판단 기준 | GET | POST |
|---|---|---|---|
| 연결 실패 | `connect` 실패 또는 1초 안에 연결 안 됨 | 같은 그룹 다른 서버로 1회 재시도. 대체 서버가 없으면 **502** | GET과 같음 (요청이 서버에 닿지 않았으므로 안전) |
| 응답 멈춤 | 요청을 보낸 뒤 3초 동안 응답 없음 | 같은 그룹 다른 서버로 1회 재시도. 대체 서버가 없거나 재시도도 실패하면 **504** | **504**, 재시도 안 함 (주문이 두 번 처리될 위험) |
| 응답 없음 | 요청을 보낸 뒤 한 바이트도 받지 못하고 연결이 닫히거나 끊김 | 같은 그룹 다른 서버로 1회 재시도. 대체 서버가 없거나 재시도도 실패하면 **502** | **502**, 재시도 안 함 (요청이 이미 전달돼 처리됐는지 알 수 없음) |
| 이상 응답 | 응답을 받았지만 상태 줄이 HTTP 형식이 아님 | **502**, 재시도 안 함 | **502**, 재시도 안 함 |
| 그룹 전체 제외 | 보낼 서버가 없음 | **503** | **503** |
| 백엔드 과부하 | 백엔드가 503을 돌려줌 | 그대로 전달 | 그대로 전달 |

- 재시도 대상: 같은 그룹에서 **방금 실패한 서버를 뺀** 제외되지 않은 서버 중 Round-Robin 다음 순서.
- 재시도는 최대 1회입니다.
- 이상 응답에서 재시도하지 않는 것은 Nginx 기본 동작(`proxy_next_upstream error timeout`)과 같습니다.
- 응답 없음에서 GET을 재시도하는 것도 Nginx와 같습니다(Nginx는 응답 없이 끊긴 연결을 `error`로 봄). POST는 Nginx도 기본적으로 다시 보내지 않습니다.

### 5.7 헬스 체크

- 별도 스레드가 2초마다 모든 서버에 `GET /health`를 보냅니다. 연결·응답 제한 시간은 1초.
- 200이 아니거나, 시간 안에 응답이 없거나, 잘못된 응답이면 실패입니다.
- **연속 2회 실패 → 제외**, 제외된 서버가 **1회 성공 → 복귀**.
- 제외·복귀가 일어나면 이벤트 허브에 `sys` 이벤트를 보냅니다(7장).

### 5.8 동시성, 끊김, 종료

| 항목 | 처리 |
|---|---|
| 동시성 | 연결마다 스레드 하나(detached `pthread`). SSE 연결도 스레드 하나가 맡음 |
| keep-alive | 지원하지 않음. 요청 하나를 처리하면 연결을 닫음(`Connection: close`) |
| 클라이언트 끊김 | `SIGPIPE` 무시. 쓰기 실패 시 백엔드 연결과 메모리를 정리하고 스레드 종료. Proxy 전체는 죽지 않음 |
| 종료 | `SIGINT`·`SIGTERM`을 받으면 새 연결을 받지 않고 정리 후 종료 |
| 요청 제한 | 헤더 8KB 초과 → 400, URI 2048자 초과 → 414, 본문 1MB 초과 → 413, 요청 줄 형식이 틀리면 400, GET·POST 외 메서드는 405 |

### 5.9 구현하며 정한 사항

2·3단계를 구현하며 SPEC에 없던 부분을 아래처럼 정했습니다.

| 항목 | 결정 |
|---|---|
| route 여러 개가 맞을 때 | 접두사가 가장 긴 규칙을 고름 |
| `/` 로 끝나지 않는 접두사 | `/orders`는 `/orders`와 `/orders/...`만 받음. `/ordersX`는 받지 않음(404) |
| 폴더 요청 | `/static/`처럼 폴더를 요청하면 `403` |
| 정적 파일 메서드 | GET 외에는 `405` (`GET /`의 302도 같음) |
| 설정 숫자 항목 | 빠지면 5.1의 값을 기본으로 씀. `listen`, `static_root`, `route`(1개 이상)는 꼭 있어야 함 |
| 백엔드로 보내지 않는 헤더 | `Connection`, `Keep-Alive`, `Proxy-Connection`, `Expect` (본문은 Proxy가 이미 다 받았으므로 `Expect`가 필요 없음) |
| 기존 `X-Forwarded-For` | 있으면 그 뒤에 `, <클라이언트 IP>`를 덧붙임 |
| 백엔드 응답 크기 | 2MB를 넘으면 잘못된 응답(`502`) |
| 종료 대기 | `SIGINT`·`SIGTERM` 뒤 처리 중인 연결을 최대 5초 기다리고 종료 |
| 로그 | 기본은 에러 응답(4xx·5xx)과 상태 변화(시작·종료 등)만. `./proxy -c proxy.conf -v`면 모든 요청을 한 줄씩 |
| `X-*` 헤더를 붙이는 응답 | Proxy가 보내는 모든 응답(전달, 정적, Proxy가 만든 에러) |
| `GET /`의 302 | `X-Route: static` |
| Proxy가 만든 에러의 `X-Upstream` | `-` (최종으로 응답한 서버가 없음). 규칙이 없는 404, 요청 제한 에러는 `X-Route: -` |
| 백엔드로 보내다 실패 | 연결은 됐지만 요청 쓰기가 실패하면 `connect_fail`(요청이 닿지 않았다고 봄). 한 바이트도 못 받고 닫히거나 끊기면 `no_response`, 일부만 받고 끊기거나 크기 초과면 `bad_response` |
| 백엔드가 503을 줄 때 | HTTP 응답은 받았으므로 `X-Tries`는 `ok`, 그대로 전달 |
| 연결 제한 시간 | 시도마다 따로 1초 (재시도도 새로 1초). non-blocking `connect` + `poll` |
| 응답 제한 시간 | 요청을 다 보낸 시점부터 응답 EOF까지 전체 3초. 요청 쓰기에도 3초 제한(`SO_SNDTIMEO`) |
| 재시도 뒤 최종 상태 | 마지막 시도의 결과로 정함: `connect_fail`·`bad_response` → 502, `timeout` → 504 |
| 헬스 체크 방식 | 서버마다 확인 스레드 하나. 확인을 **시작한** 시각 기준 2초 간격이라, 멈춘 서버가 있어도 다른 서버는 늦어지지 않음 |
| 헬스 체크 제한 시간 | 연결 1초, 응답 1초 각각 (`health_timeout_ms`) |
| 헬스 체크 실패 이유 | `연결 실패`, `응답 없음`(시간 초과, 또는 한 바이트도 못 받고 닫힘·끊김 = `no_response`), `이상 응답`(받았지만 HTTP 형식 아님), `상태 NNN`(200이 아님) |
| 상태 변화 알림 | `events_sys()` 한 함수로 모음. 지금은 시각을 붙여 로그로만, 6단계에서 SSE `sys`로도 보냄. 메시지에는 서버 id를 씀(예: `헬스 체크: products-2 제외 (응답 없음)`) |
| `-v`의 헬스 체크 로그 | 확인할 때마다 시각과 결과(`ok`, `실패 (이유, 연속 N회)`)를 남김 |
| 종료 순서 | 새 연결 받기 중단 → 헬스 체크 스레드 멈춤(진행 중인 확인이 끝날 때까지 최대 약 2초) → 처리 중인 연결 대기(최대 5초) |
| 캐시 키 | 요청의 경로 부분만(`?` 뒤 쿼리는 무시). `/products/2?x=1`은 `/products/2`와 같은 항목 |
| 캐시 대상 숫자 | `/products/` 뒤가 숫자로만 이루어진 경우(자릿수 제한 없음). `/products/1/stock`, `/products/abc`는 아님 |
| 캐시 HIT 응답 | 저장된 백엔드 응답(헤더+본문)에 `X-Route: products`, `X-Upstream: -`, `X-Tries: `(빈 값), `X-Cache: HIT`를 붙여 보냄. 본문의 `server`는 처음 받아 온 서버 그대로 |
| 캐시 MISS 뒤 에러 | 백엔드가 실패하면(502·503·504) 저장하지 않고 `X-Cache: MISS`로 에러를 돌려줌. 백엔드가 준 503도 저장하지 않음(200만 저장) |
| HIT와 헬스 체크 | 캐시 확인이 서버 선택보다 먼저라, 그룹 서버가 모두 멈추거나 제외돼도 TTL 동안은 HIT로 응답 |
| 동시 MISS | 같은 항목이 비어 있을 때 동시에 온 요청은 각자 백엔드에 감(요청 합치기 없음). 마지막에 받은 응답이 저장됨 |
| 만료 항목 정리 | 조회할 때 만료된 항목은 지우고, 저장할 때 만료된 항목을 모두 지움. 항목 수 상한 1024개(넘으면 가장 오래된 것부터 지움) |
| 캐시 시작 상태 | 꺼짐. 시험용으로 `./proxy -c proxy.conf -C`(또는 `./run.sh -C`)면 켠 채 시작 |
| 캐시 통계 | `cache_get_stats()`: HIT 수, MISS 수, 저장 수, 현재 항목 수 (6단계 화면용) |

## 6. 데모 제어부

### 6.1 트래픽 생성기 (loadgen)

- proxy 프로세스 안의 스레드. 3장의 비율과 도착 간격으로 요청을 만듭니다.
- 요청 하나마다 detached 스레드가 일반 HTTP 클라이언트처럼 요청을 보내고 응답을 읽습니다. 클라이언트 쪽 제한 시간은 10초. 동시에 도는 요청 스레드는 최대 500개로 제한합니다.
- 보내는 곳:
  - **Proxy 켬:** `127.0.0.1:8080` (Proxy를 거침)
  - **Proxy 끔:** 모든 요청을 `127.0.0.1:8001`(상품 서버 1)로 직결. 주문도 상품 서버 1로 감
- 응답을 받으면 상태 코드, 걸린 시간, 응답 헤더(`X-Route`, `X-Upstream`, `X-Tries`, `X-Cache`)로 `req` 이벤트를 만들어 이벤트 허브에 보냅니다.
- 응답을 못 받으면(연결 실패, 10초 초과, HTTP 형식이 아님) `status`를 `"ERR"`로 둡니다.

### 6.2 세일 진행

| 상태(sale) | 의미 | 트래픽 |
|---|---|---|
| `pre` | 세일 전 (시작 상태) | 초당 1건 |
| `count` | "세일 시작"을 누른 뒤 5초 카운트다운 | 초당 1건 |
| `on` | 세일 중 | 슬라이더 값 |

### 6.3 제어 API (브라우저 → proxy)

모두 `POST`, 응답은 `200 OK`와 `{"ok":true}`. 잘못된 값이면 400.

| API | 동작 |
|---|---|
| `/api/control/sale` | `pre`일 때만 카운트다운 시작 |
| `/api/control/rate?value=0..100` | 세일 중 트래픽 양 |
| `/api/control/proxy?on=1\|0` | 트래픽 생성기의 보내는 곳을 바꿈 |
| `/api/control/cache?on=1\|0` | 캐시 켜기·끄기 (끄면 비움) |
| `/api/control/server?id=products-2&mode=normal\|hang\|bad` | 해당 백엔드의 `/__admin/mode`를 호출 |
| `/api/control/reset` | 시작 상태로 되돌림: 세일 `pre`, 트래픽 50, Proxy 켬, 캐시 끔·비움, 모든 서버 normal, 제외 해제, 백엔드 `done` 카운터 0 (각 백엔드의 `/__admin/reset` 호출) |

### 6.4 구현하며 정한 사항

6단계를 구현하며 SPEC에 없던 부분을 아래처럼 정했습니다. (이벤트 허브는 7.4)

| 항목 | 결정 |
|---|---|
| `sale`을 다시 누를 때 | 카운트다운·세일 중이면 아무것도 바꾸지 않고 `200 {"ok":true}` |
| `rate` | 언제든 바꿀 수 있지만, 실제로 쓰이는 것은 세일 중(`on`)일 때. `0`이면 요청을 만들지 않음 |
| 카운트다운 | `countdown`은 5 → 1, 카운트다운이 아니면 0. 5초가 지나면 바로 `on` |
| 도착 간격 | 지수 분포. 기다리는 중에 rate가 바뀌면 남은 간격을 새 rate로 다시 뽑음(지수 분포는 기다린 시간과 무관하므로 포아송 도착이 유지됨) |
| 동시 요청 상한 500 | 넘으면 그 요청은 만들지 않고 건너뜀. 건너뛴 수는 종료할 때 로그에 남김 |
| 주문 본문 | `{"product_id":N,"qty":1}` |
| `req`의 `t`·`latency_ms` | `t`는 요청을 시작한 시각, `latency_ms`는 연결 시작부터 응답 끝(EOF)까지 |
| Proxy 거침 + 응답 없음 | `status:"ERR"`, `route:"-"`, `upstream:null`, `tries:[]`, `cache:"BYPASS"` |
| 직결의 `tries.result` | 트래픽 생성기가 본 결과: HTTP 응답을 받으면(503 포함) `ok`, 아니면 `connect_fail`·`timeout`(10초)·`no_response`·`bad_response` (뜻은 5.4 표와 같음) |
| 백엔드 상태 읽기 | 0.5초마다 서버를 차례로 읽음(서버당 0.3초 제한). 실패하면 이전 값 유지 |
| 과부하·회복 sys | status를 읽을 때 `overloaded`가 바뀐 것을 보고 보냄 (0.5초 단위) |
| 제어 API 에러 | 본문 `{"ok":false,"error":"이유"}`. 없는 API 404, POST가 아니면 405, 서버 모드를 바꿀 백엔드에 연결할 수 없으면 502 |
| sys 문구 | `세일 카운트다운 시작 (5초)`, `세일 시작!`, `Proxy 켜짐`, `Proxy 꺼짐: 모든 요청을 상품 서버 1로 직결`, `캐시 켜짐 (TTL 10초)`, `캐시 꺼짐 (저장된 내용 비움)`, `서버 모드: 상품 서버 2 → 응답 멈춤`, `과부하: 상품 서버 1 다운 (새 요청에 503)`, `과부하 회복: 상품 서버 1`, `초기화` |
| reset 중 꺼진 백엔드 | 건너뛰고 `초기화 (백엔드 N대는 응답이 없어 초기화하지 못함)` |
| 에러 로그 묶기 | `-v`가 없으면 같은 종류(상태 코드 + 그룹)의 에러는 1초에 3줄까지 찍고, 나머지는 `(같은 에러 N건 더: 503 route=products, 1초 동안)` 한 줄로. 상태 변화 로그는 묶지 않음 |
| 종료 순서 | 새 연결 중단 → 트래픽 생성기(새 요청 중단, 진행 중 요청은 기다리지 않음) → status 스레드 → 헬스 체크 → 이벤트 연결 → 처리 중 연결 대기(최대 5초) |

## 7. 화면이 받는 데이터 형식 (SSE)

브라우저는 `GET /api/events`에 `EventSource`로 연결합니다. Proxy는 `Content-Type: text/event-stream`으로 연결을 열어 두고, 이벤트마다 `data: <JSON>\n\n`을 보냅니다. 연결이 끊기면 그 클라이언트만 정리합니다.

### 7.1 `req` · 요청 하나가 끝났을 때 (트래픽 생성기가 보냄)

```json
{"type":"req","id":1532,"t":1764050000123,
 "method":"GET","path":"/products/2/stock","kind":"stock",
 "via":"proxy","route":"products","upstream":"products-3",
 "tries":[{"server":"products-2","result":"timeout"},{"server":"products-3","result":"ok"}],
 "cache":"BYPASS","status":200,"latency_ms":3312}
```

| 필드 | 값 |
|---|---|
| `kind` | `detail` / `stock` / `order` |
| `via` | `proxy` / `direct` (Proxy 끔) |
| `route` | `products` / `orders` / `-` |
| `upstream` | 최종 응답 서버 id, 없으면 `null` |
| `tries` | `X-Tries`를 펼친 것. 캐시 HIT면 빈 배열. direct면 `[{"server":"products-1","result":"ok"}]` 같은 형태. `result`는 `ok` / `timeout` / `connect_fail` / `no_response` / `bad_response` (5.4) |
| `cache` | `HIT` / `MISS` / `BYPASS` |
| `status` | 숫자 상태 코드 또는 `"ERR"` |

### 7.2 `status` · 0.5초마다 (proxy가 보냄)

```json
{"type":"status","proxy_on":true,"cache_on":false,
 "sale":"count","countdown":3,"rate":50,
 "next":{"products":"products-2","orders":"orders-1"},
 "servers":[
  {"id":"products-1","group":"products","mode":"normal","excluded":false,
   "fails":0,"active":3,"queue":0,"overloaded":false,"done":120}
 ]}
```

`servers`의 `active`, `queue`, `overloaded`, `done`, `mode`는 proxy가 각 백엔드의 `/__admin/stats`를 0.5초마다 읽어 채웁니다. 읽기에 실패하면 이전 값을 유지합니다.

### 7.3 `sys` · 상태 변화 알림

```json
{"type":"sys","t":1764050000123,"level":"bad","msg":"헬스 체크: 상품 서버 2 제외 (응답 없음)"}
```

보내는 때: 헬스 체크 제외·복귀, 세일 시작, 카운트다운 시작, Proxy·캐시 켜기·끄기, 서버 모드 변경, 백엔드 과부하·회복 감지, 초기화.

`level`은 화면 알림의 테두리 색을 정하는 값입니다. 화면은 문구가 아니라 이 값으로 색을 정합니다.

| level | 뜻 | 보내는 때 |
|---|---|---|
| `bad` | 나쁜 소식 (빨강) | 헬스 체크 제외, 백엔드 과부하, 서버 모드를 멈춤·이상 응답으로, 초기화하지 못한 백엔드가 있음 |
| `good` | 좋은 소식 (초록) | 헬스 체크 복귀, 과부하 회복, 서버 모드를 정상으로 |
| `info` | 그 밖 (회색) | 세일 카운트다운·시작, Proxy·캐시 켜기·끄기, 초기화 |

서버 이름: 화면으로 보내는 `msg`에는 서버 id 대신 한국어 이름을 씁니다. `products-N` → "상품 서버 N", `orders-N` → "주문 서버 N". 터미널 로그에는 지금처럼 id를 씁니다(예: 로그 `헬스 체크: products-2 제외 (응답 없음)` ↔ 화면 `헬스 체크: 상품 서버 2 제외 (응답 없음)`).

### 7.4 이벤트 허브 구현하며 정한 사항

| 항목 | 결정 |
|---|---|
| 막힘 방지 | 이벤트를 만드는 쪽은 클라이언트마다 있는 대기열에 넣기만 함. 소켓 쓰기는 그 이벤트 연결을 맡은 스레드가 lock 밖에서 함 |
| 느린 클라이언트 | 대기열이 1000개(초당 100건이면 약 10초분)를 넘거나, 한 번 쓰기가 2초 넘게 막히면 그 연결만 끊음 |
| 연결 유지 | 15초 동안 보낼 것이 없으면 `: ping` 주석 줄을 보냄. 연결 직후 `: connected`를 보냄 |
| 응답 헤더 | `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-cache`, `Content-Length` 없음 |
| 터미널 로그 | 이벤트 연결이 생기거나 끊길 때 연결 수와 함께 한 줄 |
| `GET`이 아닌 `/api/events` | `405` |

### 8.2 애니메이션

| 상황 | 표현 |
|---|---|
| 요청 | 조회는 카트, 주문은 상자 아이콘. 사용자들 → Proxy → 서버로 이동. 한 구간 0.6초 |
| 재생 방식 | `req` 이벤트를 받으면 그 결과를 느리게 다시 그림. 그릴 확률은 일반 요청 `min(1, 12/rate)`, 중요한 요청(HIT, 재시도, 에러) `min(1, 30/rate)` |
| Cache HIT | Proxy에서 바로 되돌아오고 보라색 `HIT` 배지 |
| 응답 멈춤 + GET 재시도 | 멈춘 서버 안에서 원형 타이머 3초 → 같은 그룹 다른 서버로 점선 이동, "재시도 · 타임아웃" 배지 |
| 응답 멈춤 + POST | 원형 타이머 3초 → 빨갛게 변해 사용자에게 돌아옴, `504` 배지 |
| 이상 응답 | 서버에 닿았다가 빨갛게 변해 사용자에게 돌아옴, `502` 배지 |
| 응답 없음 + GET 재시도 | 서버에 닿았다가 같은 그룹 다른 서버로 점선 이동, "재시도 · 응답 없음" 배지 |
| 응답 없음 + POST | 서버에 닿았다가 빨갛게 변해 사용자에게 돌아옴, `502` 배지 |
| 연결 실패 + 재시도 | 서버 앞에서 ✕ 후 다른 서버로 꺾임, "재시도 · 미전달" 배지 (UI 조작으로는 나오지 않지만 이벤트가 오면 그림) |
| 그룹 전체 제외 | Proxy에서 바로 돌아옴, `503` 배지 |
| 헬스 체크 | 실패 중인 서버 연결선은 빨간 점선, 제외되면 연결선이 사라지고 "제외됨" 배지, 복귀하면 초록 연결선과 "복귀" 배지 1.6초 |
| 상태 알림 | `sys` 이벤트가 오면 흐름 화면 위쪽 가운데(왼쪽 위 타이머와 오른쪽 위 범례 사이)에 크게(26px) 띄움. 3초 보였다가 1초 동안 서서히 사라짐. 최대 3개를 위아래로 쌓고 새 알림이 위. 흰 배경·검정 글씨, 테두리는 sys의 `level`로: `bad` 빨강, `good` 초록, `info` 회색(7.3). 로그에도 회색 줄로 그대로 남김 |
| Proxy 끔 | Proxy 상자가 흐려지고 "OFF", 사용자들 → 상품 서버 1 빨간 점선 직결 |

### 8.3 서버 상자

이름, "처리 N건", 부하 게이지(`(active+queue)/8`, 0.55 이상 주황, 0.85 이상 빨강, 부드럽게 변화), "동시 a/8 · 대기 q". 멈춤이면 주황 테두리와 "응답 멈춤", 이상 응답이면 빨간 테두리와 "이상 응답", 과부하면 빨간 테두리와 "과부하". 그룹 상자 머리글에 그룹 이름, 경로, "다음: 서버 N"(`status.next`).

### 8.4 패널

| 패널 | 내용 |
|---|---|
| 통계 | 초당 요청(최근 1초 `req` 수), 누적, Cache Hit(`HIT 수 / GET 수`, 캐시 꺼짐이면 `-`), 에러(상태 500 이상 또는 ERR), 평균 응답(최근 성공 150건 평균) |
| 로그 | `GET /products/2/stock → 상품 서버 2 타임아웃 → 상품 서버 3 재시도 · 200 · 3312ms` 형식. 최근 100줄. 에러 빨강, HIT 보라, 재시도 갈색, `sys`는 회색. **마우스를 올리면 스크롤 멈춤** |
| 요청 상세 | 로그 줄을 누르면 메서드, 경로, 상태 코드, 요청 시각(HH:MM:SS.mmm) |

### 8.5 조작 바

[세일 시작] · 트래픽 슬라이더(0~100, 기본 50, "N건/초") · Proxy 스위치 · 캐시 스위치 · "서버 상태" 상품 [1][2][3] 주문 [1][2] · [초기화]

- 서버 버튼을 누르면 버튼 바로 위에 작은 메뉴 **[정상 | 멈춤 | 이상 응답]**이 뜹니다. 지금 상태인 항목은 굵은 테두리로 표시하고, 항목을 누르면 그 모드로 `/api/control/server`를 한 번만 호출하고 닫습니다. 메뉴 바깥을 누르거나 Esc를 누르면 그냥 닫습니다.
- 메뉴 항목도 8.1 버튼 규칙(흰 배경, 검정 글씨, 버튼과 같은 글자 크기)을 따르고, 멈춤은 연주황, 이상 응답은 연분홍 배경입니다.
- 버튼 상태(색)는 `status` 이벤트의 값으로 맞춥니다(초기화 후에도, 탭을 여러 개 열어도 일치하도록).

### 8.6 모의 모드 (발표 백업)

`demo.html?mock=1`로 열면 서버 없이 prototype처럼 화면 안에서 동작을 흉내 냅니다. 실제 서버가 발표장에서 안 돌 때를 대비한 백업입니다. 화면 상단에 작게 "모의 모드"라고 표시합니다. 기본(파라미터 없음)은 실제 서버 모드입니다.

### 8.7 구현하며 정한 사항

| 항목 | 결정 |
|---|---|
| 구조 | [이벤트 공급기] → `handleEvent()` → 화면 상태 → 그리기. 실제 모드는 SSE가, 모의 모드는 화면 안의 "가짜 이벤트 공급기"가 SPEC 7장 형식의 이벤트를 만듦. 그리기 코드는 하나 |
| 위쪽 가운데 알림 | SSE가 끊기면 빨간 "서버 연결 끊김", 다시 연결되면 지움(브라우저가 자동으로 다시 연결). 모의 모드는 회색 "모의 모드" |
| 제어 실패 | 제어 API가 실패하면 로그에 회색 줄 `제어 실패: 이유` |
| 화면 상태의 출처 | 스위치·서버 버튼 색·타이머·슬라이더는 status 값으로만 맞춤(버튼을 누른 탭이 직접 바꾸지 않음) |
| 트래픽 슬라이더 | 값 보내기는 150ms에 한 번. 끄는 동안과 마지막 조작 뒤 1초는 status가 값을 되돌리지 않음 |
| 서버 버튼 → 메뉴 (prototype과 다른 점) | prototype은 누를 때마다 정상 → 멈춤 → 이상 응답으로 돌았지만, 이상 응답으로 가려면 멈춤을 거쳐야 해서 그 사이에 헬스 체크로 먼저 제외되는 문제가 있었음. 그래서 메뉴에서 원하는 모드를 바로 고르게 바꿈(8.5). 메뉴는 `.bar` 안에 있고 누른 버튼의 왼쪽에 맞춰 뜸 |
| 상태 알림 (prototype과 다른 점) | prototype은 sys를 로그에만 남겼지만, 초당 100건이면 sys 줄이 약 1초 만에 로그에서 밀려나므로 흐름 화면에도 크게 띄움(8.2) |
| 브라우저 쪽 알림 | 서버가 보내지 않는 알림도 같은 방식으로 띄우고 level은 화면이 직접 정함: `서버 연결 끊김`(bad), `서버 다시 연결됨`(good), `제어 실패: 이유`(bad). 끊김·재연결은 바뀔 때 한 번만 |
| 알림 색 판단 | 문구가 아니라 sys의 `level` 값으로 정함(7.3). 문구를 바꿔도 색이 틀어지지 않음. 모의 모드 공급기도 같은 level을 보냄 |
| 경로 그리기 | `tries`를 차례로: `timeout`은 서버 안 원형 타이머 3초, `connect_fail`은 서버 앞 ✕, `no_response`·`bad_response`는 서버 입구. 다음 시도는 점선 + "재시도 · 타임아웃/미전달/응답 없음" 배지. 마지막이 실패거나 백엔드가 5xx를 주면 상태 코드 배지를 달고 빨갛게 사용자에게 |
| 직결 응답 멈춤 | 실제 제한 시간은 10초지만 화면의 원형 타이머는 3초로 그리고 `ERR`로 돌아옴 |
| 아이콘 수 | 동시에 움직이는 아이콘 최대 300개. 탭이 안 보이는 동안은 새로 쌓지 않음(돌아왔을 때 한꺼번에 쏟아지지 않게) |
| 로그 | 1초에 4번 묶어서 다시 그림. 문장: `GET /products/2/stock → 상품 서버 2 타임아웃 → 상품 서버 3 재시도 · 200 · 3312ms`. MISS면 끝에 `· MISS`, 백엔드 503이면 `과부하`, 보낼 서버가 없으면 `상품 그룹 보낼 서버 없음`, 직결이면 `상품 서버 1 직결` |
| 통계 | 에러 = 상태 500 이상 또는 ERR. Cache Hit은 캐시를 켜거나 끌 때 0부터 다시 셈. 평균 응답은 최근 200 응답 150건 |
| 초기화 | sys `초기화`를 받으면 모든 탭이 통계·로그·선택을 비움 |
| 모의 모드 규칙 | SPEC 4~7장의 숫자와 재시도 규칙, sys 문구를 그대로 흉내 냄. status는 0.5초마다와 조작 직후. 헬스 체크는 2초마다 모드만 보고 판단 |
| sys 줄과 로그 100줄 | 초당 100건이면 sys 줄도 약 1초 뒤 로그에서 밀려남 (로그는 최근 100줄). 그래서 흐름 화면의 상태 알림으로도 보여 줌 |

## 11. 범위 밖

과제 전문에 있지만 이번에는 하지 않는 것: keep-alive, HTTPS, CGI, I/O 멀티플렉싱(`epoll` 등), Forward Proxy, 단위 테스트·부하 테스트 도구 연동(시간이 남으면 추가).
