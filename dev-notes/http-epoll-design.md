# Linux epoll 웹서버 설계

## 목표와 범위

TCP 연결을 받고, HTTP/1.1의 GET과 POST를 직접 파싱해 응답한다. 일반 GET은 지정한 루트에서 파일을 읽고, `POST /api/echo`는 받은 본문을 바탕으로 응답을 만든다. 한 클라이언트가 입력을 멈춰도 다른 클라이언트가 응답을 받을 수 있어야 한다.

동시 연결은 **Linux의 단일 스레드 Level-Triggered `epoll` 이벤트 루프**로 처리한다. 기존 스레드 풀 계획은 이 설계로 대체한다. 이전 `poll()` Echo는 TCP 동작을 검증한 기준이다. [TCP 설계](tcp-server-design.md)와 [첫 GET의 파서 계약](http-get-design.md)에서 확정한 부분 송수신, 헤더 경계, 16 KiB 한도, EOF와 종료 처리 정책을 이어 쓴다.

| 항목 | 이번 단계의 완료 기준 |
|---|---|
| TCP 소켓 서버 | `socket()` → `bind()` → `listen()` → `accept()`로 연결을 받고, 같은 연결에서 요청 바이트와 응답 바이트를 송수신한다. |
| HTTP 요청 파싱 | 요청 라인과 `Host`, `Content-Length`, `Connection`을 해석한다. POST의 본문 경계를 판단하고 선언된 길이까지 누적한다. |
| HTTP 응답 생성 | 상태 라인, `Content-Type`, `Content-Length`, `Connection` 및 본문이 실제 응답에 나타난다. |
| 정적 파일 | 지정한 루트의 HTML, CSS, JS, PNG, JPG를 올바른 MIME 타입으로 보낸다. 파일 없음, 접근 금지, 내부 오류를 구분한다. |
| 동적 요청 | `POST /api/echo`는 본문을 전부 받은 뒤, 요청에 따라 그 바이트로 응답을 만든다. |
| 동시 요청 | A가 미완성 헤더를 보낸 뒤 대기 중이어도 B가 정상 응답을 먼저 받는다. |

## 실행과 파일 구성

Linux에서 `make`한 뒤 실행한다. `./tiny-web-server 8080`은 Echo 모드이고, `./tiny-web-server 8080 ./public`은 HTTP 모드다. 포트는 기존대로 1~65535에서 검증하고, 문서 루트는 시작할 때 디렉터리 FD로 열어 둔다. 로컬 검증은 `127.0.0.1`에서 한다. Docker 개발 시 컨테이너 안에서 서버와 테스트 클라이언트를 실행한다.

| 모듈 | 책임 |
|---|---|
| `main.c` | 포트와 루트 인자 검사, 서버 진입점 호출 |
| `tcp_server.c` | 소켓과 `epoll` 준비, 이벤트 분배, 연결 상태 소유, 종료 처리 |
| `http_request.c` | 소켓과 독립적인 헤더 경계 탐색 및 요청 파싱 |
| `http_response.c` | 상태, 본문, 연결 종료 정책에 맞춰 응답 헤더 작성 |
| `static_file.c` | 루트 내부에서 파일 열기, 파일 정보와 MIME 타입 확인, 파일 접근 오류 분류 |

진입점과 전체 요청 흐름을 파일 위쪽에 두고 세부 처리를 아래에 둔다. 호출이 어떤 검증이나 정책을 표현할 때 함수를 나눈다. 이벤트 등록이나 모듈 사이에서 인자만 전달하는 함수는 만들지 않는다.

| 호출 | 입력과 결과 |
|---|---|
| `tcp_server_run(port, root_path)` | 검증한 포트와 문서 루트를 받는다. 정상 종료는 `0`, 서버 준비나 이벤트 루프 실패는 `-1`이다. |
| `handle_client_event(connection, events)` | 준비된 방향의 처리를 진행한다. 다음 이벤트를 기다리거나, 응답 준비로 넘어가거나, 해당 연결을 닫는다. |
| `parse_http_request(buffer, header_end)` | 완성된 헤더를 검사한다. 파싱 상태와 요청 구조체를 돌려준다. HTTP 응답은 호출하는 쪽에서 결정한다. |
| `open_static_file(root_fd, path)` | 파일 FD와 크기를 반환한다. 실패하면 파일 없음, 접근 금지, 내부 오류로 분류한다. 성공 시 파일 FD의 소유권은 연결로 넘어간다. |
| `build_response_headers()` | 상태, 본문 유형과 길이, 연결 종료 여부를 바탕으로 응답 헤더를 작성한다. 본문은 연결의 송신 단계에서 처리한다. |

## TCP와 epoll 이벤트 루프

```text
tcp_server_run
  └─ epoll_wait
      ├─ 리스닝 소켓 → accept_ready_clients → 연결별 상태 등록
      └─ 클라이언트 → handle_client_event
          ├─ 입력 → 헤더 누적 → 파싱 → 필요하면 POST 본문 누적
          ├─ 응답 준비 → GET 파일 또는 POST 동적 응답 선택
          └─ 출력 → 헤더와 본문 송신 → 다음 요청 처리 또는 연결 정리
```

1. 기존대로 IPv4 리스닝 소켓을 만들고 `SO_REUSEADDR` 설정, `bind()`, `listen(fd, 16)`을 수행한다. 리스닝 FD와 각 클라이언트 FD를 논블로킹으로 설정한다. 클라이언트 주소와 포트 로그는 계속 남긴다.
2. `epoll_create1(EPOLL_CLOEXEC)`을 호출하고 리스닝 FD를 `EPOLLIN`으로 등록한다. 리스닝 이벤트에서 연결을 수락해 새 클라이언트를 등록한다. 수락은 `EAGAIN`까지 진행하되 한 번의 이벤트에 최대 16개로 제한한다.
3. 클라이언트는 `READ_HEADERS` → 필요 시 `READ_BODY` → `WRITE_RESPONSE` 순서로 이동한다. 읽을 때 `EPOLLIN | EPOLLRDHUP`을, 보낼 응답이 있을 때 `EPOLLOUT`을 감시한다. Level-Triggered 모드에서 한 번에 처리할 바이트를 제한하고 루프에 돌아와 다른 연결에 차례를 준다.
4. 쓰기 이벤트에서는 남은 위치부터 전송한다. 가능한 만큼 보낸 뒤 전부 끝나면 연결을 정리한다. `EAGAIN`이면 지금까지 보낸 위치를 보관하고 다음 쓰기 이벤트를 기다린다.
5. `SIGINT`나 `SIGTERM`을 확인하면 이전 계획대로 새 연결 수락과 남은 송수신을 중단한다. 이벤트 루프가 클라이언트, 파일, 리스닝, 문서 루트, `epoll` FD를 정리한다. `SIGPIPE`는 기존처럼 무시한다.

연결별 상태에는 FD, 현재 단계, 받은 길이, 본문 버퍼, 응답 송신 위치, 열린 파일 FD, 마감 시각을 둔다. 이벤트 루프만 상태와 FD를 소유한다. 동시 클라이언트는 128개로 제한한다. 연결 종료 시 먼저 감시 해제한 뒤 FD와 메모리를 정리한다. 이벤트에는 슬롯 번호와 세대 번호를 넣어, 방금 닫은 연결의 이벤트가 같은 번호를 재사용한 새 연결에 적용되는 것을 막는다. 새 연결을 받을 공간이 없으면 `503`을 보낼 수 있을 때만 보내고 바로 닫는다.

`EPOLLERR`인 클라이언트는 그 연결만 정리한다. 읽기 중 끊김 표시를 받으면 `recv()`를 시도해 남은 데이터를 먼저 확인한다. 실제 `recv() == 0`으로만 EOF를 판단한다. 상대의 송신만 끝난 경우에는 응답 전송을 시도할 수 있다. 완전히 끊긴 연결에서 진행할 수 없으면 닫아 같은 끊김 이벤트를 반복 처리하지 않는다. 리스닝 소켓이나 `epoll_wait()` 자체의 회복 불가능한 오류는 서버의 실패로 올린다. [Linux epoll 동작 모드](https://man7.org/linux/man-pages/man7/epoll.7.html) · [이벤트와 등록 규칙](https://man7.org/linux/man-pages/man2/epoll_ctl.2.html)

### 수신 계약의 변경

`RecvResult`는 데이터와 길이(`RECV_DATA`), 실제 EOF(`RECV_EOF`), 서버 종료 요청(`RECV_STOP`), 복구할 수 없는 수신 실패(`RECV_ERROR`)를 구분한다. 논블로킹 수신에서 `EAGAIN` 또는 `EWOULDBLOCK`이면 `RECV_AGAIN`으로 이벤트 루프에 돌아간다. `epoll_wait()` 자체의 실패는 이벤트 루프가 처리한다. 수신 함수는 연결을 닫거나 HTTP 오류 응답을 고르지 않는다.

## HTTP 파싱과 POST 본문

1. 헤더 버퍼에 받은 바이트를 이어 붙이고, 독립 함수 `find_header_end(buffer, used)`로 첫 `\r\n\r\n` 바로 뒤 위치를 찾는다. 먼저 경계를 검사하므로 정확히 16 KiB에서 끝나는 헤더도 받을 수 있다. 가득 찼는데 경계가 없으면 `431`을 보낸다.
2. `parse_http_request(buffer, header_end)`가 메서드, 요청 대상, 버전, `Host`, 본문 길이, `Connection` 토큰을 검증해 요청 구조체를 반환한다. 헤더 이름과 연결 토큰은 대소문자를 구분하지 않는다. 버퍼를 참조하는 필드는 읽기 전용 포인터와 길이로 보관한다. 요청을 처리하는 연결만 버퍼를 소유하며, 참조가 살아 있는 동안 버퍼를 덮어쓰지 않는다.
3. HTTP/1.1의 `Host` 누락·중복·유효하지 않은 값과 잘못된 요청 형식은 `400`이다. `Content-Length`는 10진수이고, 중복 또는 `Transfer-Encoding`과 동시 선언하면 거부한다. 길이는 오버플로우 없이 제한과 비교한 뒤 필요한 범위에서만 숫자로 변환한다. 잘못된 프레이밍은 `400`, 올바르게 선언된 전송 코딩을 아직 처리할 수 없는 경우는 `501`로 닫는다.
4. POST는 유효한 `Content-Length`를 요구한다. 누락은 `411`, 1 MiB 초과는 `413`이다. 길이가 유효하면 그때 본문 공간을 준비한다. 헤더와 같이 이미 들어온 본문 중 필요한 바이트부터 포함하고 나머지를 이어 받는다. 정확히 선언된 길이를 받았을 때만 동적 요청을 처리한다. 중간 EOF는 전송 가능한 연결에 `400`을 보낸다. `Content-Length: 0`도 완료된 POST다.
5. GET에 0보다 큰 본문 길이가 선언되면 `400`을 보낸다. 정상 요청에서는 헤더와 선언된 본문 길이만 소비한다. 그 뒤의 바이트는 같은 연결의 다음 요청에 사용한다. 요청 라인과 파서의 상태 코드 정책은 [첫 GET 설계](http-get-design.md)에 기록했다.

헤더 수신은 연결을 받았을 때부터 **10초**, 본문 수신은 헤더 파싱이 끝났을 때부터 **10초**의 절대 마감 시각으로 관리한다. 시간이 지나면 가능한 경우 `408`을 준비하고, 송신에도 별도의 **10초** 한도를 둔다. 서버 종료 확인을 겸해 `epoll_wait()`는 한 번에 최대 100ms 기다리고, 매 루프에서 만료된 연결을 확인한다. 클라이언트가 조금씩 보낸다고 기한을 연장하지 않는다. [HTTP 메시지 본문 길이](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)

## 응답과 정적 파일

- 첫 HTTP 단계의 `GET /`는 `200 OK`와 `Hello`를 돌려줘서 파서를 검증한다. 정적 파일 단계가 들어오면 `GET /`을 문서 루트의 `index.html`에 매핑한다.
- 응답은 상태 라인, `Content-Type`, `Content-Length`를 포함한다. 본문 길이는 실제 바이트 수를 사용한다. 연결을 닫는 응답에는 `Connection: close`를 추가한다. 공통 응답 헤더 작성 함수에서 `Date`도 생성한다.
- `POST /api/echo`는 읽은 본문을 그대로 보낸다. 초기 응답 MIME은 `application/octet-stream`이고 빈 본문도 받을 수 있다. 서버가 구현하지 않은 메서드는 `501`로 응답한다. 문서 루트 경로에 대한 POST처럼 메서드를 알지만 그 대상에서 허용하지 않으면 `405`와 해당 경로의 `Allow`를 보낸다.
- 정적 파일은 요청 대상의 경로 부분만 사용한다. 한 번 디코딩하고, 잘못된 인코딩이나 널 바이트를 거부한다. 루트 밖을 가리킬 수 있는 경로 요소는 거부한다. 각 경로 요소를 문서 루트 FD부터 `openat()`과 `O_NOFOLLOW | O_NONBLOCK`으로 열고, 열린 FD를 `fstat()`으로 확인한다. 중간 요소는 디렉터리, 전송 대상은 일반 파일만 허용한다. 심볼릭 링크 접근은 `403`으로 분류한다. 로컬 모드의 문서 루트는 운영자가 관리하는 디렉터리다. [Linux openat과 O_NOFOLLOW](https://man7.org/linux/man-pages/man2/openat.2.html)
- 파일이 없으면 `404`, 정책상 열 수 없거나 접근 권한이 없으면 `403`, 응답 전 예상하지 못한 내부 I/O 오류는 `500`이다. 이미 응답 헤더를 보낸 뒤 파일 읽기가 실패하면 연결을 닫아 응답이 불완전함을 드러낸다.
- 확장자와 MIME은 `.html` → `text/html`, `.css` → `text/css`, `.js` → `text/javascript`, `.png` → `image/png`, `.jpg/.jpeg` → `image/jpeg`로 매핑한다. 알려지지 않은 타입은 `application/octet-stream`을 사용한다.
- 파일은 4 KiB씩 읽어 송신한다. 같은 조각의 부분 전송이 끝난 뒤 다음 조각을 읽는다. `epoll`에는 네트워크 소켓만 등록한다. 이 구현에서는 일반 파일 I/O가 이벤트 루프에서 실행되므로 느린 저장소는 다른 연결의 처리를 지연시킬 수 있다. [Linux epoll_ctl의 FD 제약](https://man7.org/linux/man-pages/man2/epoll_ctl.2.html)

## 연결 재사용

첫 HTTP 실습은 응답 한 건마다 연결을 닫았다. 이제 정상 HTTP/1.1 요청에는 같은 FD를 재사용한다. `Connection: close`가 포함된 요청이나 오류 응답은 현재 응답을 마친 뒤 연결을 닫는다. [HTTP/1.1 연결 유지 규칙](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.3)

응답 송신이 완료되면 해당 요청의 파일 FD와 POST 본문을 정리한다. 재사용할 연결에서는 입력 버퍼에 남은 바이트를 다음 요청에 사용하고, 필요한 경우 읽기 이벤트를 기다린다. 정적 파일 조각은 별도의 4 KiB 버퍼를 사용해 남은 요청 바이트를 덮어쓰지 않게 한다. 응답은 요청이 도착한 순서대로 보낸다.

다음 요청의 바이트가 없다면 응답 완료 후 5초 동안 기다린다. 5초 안에 아무것도 오지 않으면 연결을 닫아 슬롯을 반환한다. 다음 요청이 시작되면 헤더 수신에 새로 10초를 준다. 다음 요청의 일부가 이미 버퍼에 있다면 응답 완료 직후부터 헤더 기한을 계산한다.

명시적으로 연결을 닫는 응답은 송신이 끝나면 `shutdown(SHUT_WR)`로 연결의 송신 방향을 먼저 종료한다. 그 뒤 추가로 도착한 바이트는 최대 500ms 동안 버리며, 상대가 송신을 끝내면 바로 소켓을 닫는다. 읽지 않은 데이터 때문에 TCP 연결이 리셋되어 마지막 응답이 잘리는 경우를 줄인다.

## 구현 순서와 검증

| 단계 | 구현 단위 | 통과 조건 |
|---|---|---|
| 1 | 기존 Echo를 Level-Triggered `epoll` 루프로 전환 | Docker Linux에서 A가 연결만 열어 둔 동안 B가 Echo를 받는다. 이후 A도 계속 통신한다. 포트 충돌과 종료 동작도 확인한다. |
| 2 | 헤더 경계, 파서, 고정 GET 응답 | 정상 GET과 나뉜 헤더의 응답이 같다. 미완성 EOF는 `400`, 정확한 16 KiB 경계는 파싱, 경계 없이 한도에 차면 `431`이다. |
| 3 | 헤더·본문 마감 시각, POST 동적 응답 | 미완성 헤더는 기한 뒤 정리된다. 헤더와 함께 온 본문과 나뉜 본문이 같은 응답을 받는다. 누락, 크기 초과, EOF 오류, 빈 본문을 확인한다. |
| 4 | 지정 루트와 MIME별 정적 파일 | HTML·이미지 응답 헤더와 파일 원본 바이트가 일치한다. 누락, 접근 차단, 내부 오류가 각각 기대한 상태를 돌려준다. |
| 5 | 전체 HTTP에서 동시 연결과 종료 검증 | A가 헤더를 끝내기 전에 B의 정상 요청이 완료된다. B에 부분 송신이 생겨도 C가 응답을 받는다. 종료 신호 후 열린 연결을 정리한다. |
| 6 | Keep-Alive 연결 재사용 | 같은 소켓에서 응답을 여러 건 읽고, 미리 들어온 요청의 응답 순서, POST 본문 경계, 유휴 기한과 명시적 종료를 확인한다. |

파서와 MIME 매핑의 응답을 실제 TCP 연결에서 확인한다. `make test`와 `make test-sanitize`는 Echo와 HTTP 검증을 함께 실행하며 Python 3가 필요하다. Docker의 `mcr.microsoft.com/devcontainers/base:jammy` 이미지에는 GCC와 Python 3가 있다.

초기 서버는 Docker Linux에서 경고를 오류로 처리한 빌드, `make test`, GCC sanitizer와 GCC `-fanalyzer`를 통과했다. 큰 응답을 읽지 않는 연결이 있어도 다른 GET이 완료됐다. 검증용 빌드에서 부분 송신, `EINTR`, `EAGAIN`, 파일 열기 오류를 확인했다.

Keep-Alive를 적용한 뒤에도 Docker Linux에서 같은 빌드와 테스트를 통과했다. 별도 검증용 빌드에서 두 요청이 한 번의 `recv()`로 들어온 것을 확인했고, 부분 송신과 `EINTR`·`EAGAIN`을 발생시켜도 두 응답을 순서대로 받았다. Docker의 Linux 시스템 헤더를 사용한 Clang 대상 교차 정적 분석도 통과했다. 컨테이너의 런타임 sanitizer는 GCC로 실행했다.

## 팀 기준과 이후 작업

현재 동적 경로는 서버 내부의 POST 처리다. 필수 Reverse Proxy는 클라이언트 요청을 별도 백엔드 연결로 전달하는 단계에서 다룬다.
