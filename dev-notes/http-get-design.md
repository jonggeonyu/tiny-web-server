# HTTP 첫 단계 · GET /

여기서 정한 첫 GET의 요청·응답 계약은 [Linux epoll 웹서버 설계](http-epoll-design.md)에서 이어 쓴다. 연결별 수신과 응답 송신은 새 문서의 이벤트 루프 계약을 따른다.

이 단계의 목표는 TCP 연결을 통해 `GET /` 요청 한 건을 받아 HTTP 응답을 보내는 것이다. 헤더가 한꺼번에 오거나 여러 조각으로 나뉘어 오는 경우를 모두 확인한다. 현재 [TCP Echo 설계](tcp-server-design.md)를 바탕으로 진행한다.

## 요구사항과 기대 동작

| 상황 | 서버 동작 |
|---|---|
| `Host`가 있는 정상 `GET / HTTP/1.1` 요청 | 요청 헤더 전체를 받은 뒤 `200 OK`와 본문 `Hello` 5바이트를 보낸다. 응답에는 `Content-Length: 5`와 `Connection: close`를 넣고, 전송 후 연결을 닫는다. |
| 마지막 줄바꿈이 아직 도착하지 않음 | 받은 바이트를 보관하고 다음 수신을 기다린다. |
| 마지막 조각이 도착해 헤더가 완성됨 | 누적한 데이터에서 경계를 확인하고 요청을 파싱한다. 정상 요청이면 같은 `200 OK` 응답을 보낸다. |
| 16 KiB를 채웠는데도 헤더 경계가 없음 | `431 Request Header Fields Too Large`를 보내고 닫는다. |
| 헤더 일부를 받은 뒤 클라이언트가 송신만 종료함 | 서버 종료 요청이나 소켓 오류 없이 `recv()`가 EOF를 반환한 경우, 전송 가능한 연결에 `400 Bad Request`를 보내고 닫는다. |
| 현재 연결의 소켓 오류 또는 서버 종료 요청 | 기존 소켓 정리 규칙을 따른다. |

응답의 `Content-Length: 5`는 서버가 보낼 본문의 길이다. 요청의 `Content-Length`와 `Transfer-Encoding`은 이번 단계에서 검증한다. POST 본문 수신, Keep-Alive, 정적 파일, 리버스 프록시는 이후 단계에서 다룬다.

## 확정한 설계

### 1. 헤더 경계 판별을 소켓 수신과 분리

요청 처리 함수는 클라이언트 소켓에서 읽고, 수신한 바이트를 버퍼 뒤에 이어 붙인다. 헤더 경계 함수는 소켓 없이 누적 버퍼를 검사한다.

```c
size_t find_header_end(const unsigned char *buffer, size_t length);
```

- `buffer`와 `length`는 지금까지 모인 바이트와 길이다.
- 첫 `\r\n\r\n`을 찾으면 구분자 바로 다음 위치를 버퍼 시작점으로부터의 오프셋으로 반환한다. 이 위치는 나중에 요청 본문이 시작되는 지점으로 사용할 수 있다.
- 경계를 못 찾으면 `0`을 반환한다. 호출자는 기존 내용을 보존하고 다음 조각을 이어 붙인다.
- 요청 라인에서 메서드, 대상 경로, 버전을 읽고 `Host`를 확인하는 일은 경계를 찾은 뒤에 한다.

경계 판별 함수를 따로 두면 TCP 연결 없이 검사할 수 있다. 구분자가 두 번의 수신에 나뉘었을 때는 마지막 조각을 포함한 누적 버퍼를 검사한다.

### 2. 미완성 헤더에서 EOF가 확인되면 400 응답

일부 바이트를 받았고 헤더 경계를 찾지 못한 상태에서 `recv()`가 `0`을 반환하면, 클라이언트가 더 이상 요청을 보내지 않는다는 뜻이다. 상대가 송신 방향만 닫았다면 서버는 같은 연결로 `400` 응답을 보낼 수 있다. 응답 전송 중 오류가 발생하면 해당 연결을 정리한다.

현재 TCP 수신 함수는 `recv()`의 EOF, 연결 정리, 서버 종료를 모두 `0`으로 전달한다. HTTP 처리에서는 실제 EOF를 확인할 수 있도록 수신 결과를 구분해야 한다. `poll()` 자체의 실패를 서버 오류로 처리하는 기존 규칙도 유지해야 한다.

### 3. 수신 상태와 길이를 `RecvResult`로 반환

수신 함수는 클라이언트 FD, 쓸 버퍼의 시작 위치, 남은 용량을 받는다. 호출자는 남은 용량이 양수일 때만 수신 함수를 호출한다. 반환값 `RecvResult`에는 수신 상태와 이번 호출에서 받은 길이 `bytes_read`를 담는다.

| 상태 | 반환 조건 | `bytes_read` | 호출 측 처리 |
|---|---|---|---|
| `RECV_DATA` | `recv()`가 양수를 반환 | 이번에 받은 바이트 수 | 누적 길이를 늘리고 헤더 경계를 검사한다. |
| `RECV_EOF` | 양수 용량으로 호출한 `recv()`가 `0`을 반환 | `0` | HTTP 처리 함수가 누적 상태를 검사한다. 일부 헤더를 받았고 경계가 없다면 `400`을 보낸 뒤 연결 처리를 끝낸다. |
| `RECV_STOP` | 기존 정책상 해당 연결을 정리해야 하거나 서버의 종료 요청을 확인함 | `0` | HTTP 응답 없이 연결 처리를 끝낸다. 서버 종료 여부는 기존 종료 플래그로 판단한다. |
| `RECV_ERROR` | 재시도하지 않는 `poll()` 호출 오류로 서버 흐름을 계속할 수 없음 | `0` | 기존처럼 서버 수준 실패를 전달한다. |

이렇게 하면 수신 상태와 길이가 같은 호출의 결과라는 점이 호출부에 드러난다. 수신 함수는 HTTP 상태 코드를 결정하거나 FD를 닫는 책임을 갖지 않는다.

#### 기존 종료 흐름과의 연결

- `wait_for_event()`는 `poll()` 직후 서버 종료 플래그를 먼저 확인한다. 종료 요청을 확인하면 `RECV_STOP`으로 전달하고, HTTP 처리도 응답 전에 종료 요청을 확인한다.
- `POLLHUP`만으로 `RECV_EOF`를 만들지 않는다. 읽기 준비와 끊김이 함께 보고되면 기존대로 `recv()`를 시도한다. `RECV_EOF`는 실제 `recv()` 반환값으로 판정한다.
- `run_server()`는 클라이언트 처리 함수가 돌아온 뒤 클라이언트 FD를 닫는다. `RECV_ERROR`를 받은 처리 함수는 실패를 전달한다. `tcp_server_run()`은 연결 루프가 끝나면 리스닝 FD를 닫는다.
- 실제 EOF와 서버 종료는 같은 미완성 입력으로 검증한다. 클라이언트가 송신 방향만 닫으면 `400`이 와야 하고, 서버에 종료 신호를 보내면 `400` 없이 연결이 닫혀야 한다.

### 4. 요청 헤더 한도는 16 KiB

요구사항 초안에 맞춰 요청 라인부터 헤더 끝 구분자 `\r\n\r\n`까지 최대 16,384바이트를 허용한다. 새 데이터를 누적하면 먼저 경계를 찾는다. 구분자의 마지막 바이트가 정확히 16,384번째 바이트여도 파싱 단계로 넘어간다.

경계를 찾지 못했을 때 버퍼가 가득 차 있으면 `431 Request Header Fields Too Large`를 보내고 연결을 닫는다. 자리가 남으면 남은 용량 범위에서 계속 읽는다. 한도 아래에서 미완성 헤더에 실제 EOF가 오면 기존 결정대로 `400`을 보낸다.

### 5. 첫 GET 단계의 범위

선택한 조합은 `1B · 2A · 3A · 4A · 5A · 6A · 7A`다. HTTP/1.1에서 요청 대상이 정확히 `/`인 본문 없는 GET을 처리한다. 고정 응답을 전송한 뒤 연결을 닫는다. 한 바이트도 받기 전에 EOF가 오면 응답 없이 닫는다.

요청 라인은 메서드, 요청 대상, 버전을 각각 공백 한 칸으로 구분한다. 헤더 이름은 대소문자를 구분하지 않는다. HTTP/1.1에서는 유효한 `Host`가 한 줄 있어야 한다. 이 실습의 로컬 요청에는 호스트가 지정되므로 비어 있는 값은 허용하지 않는다.

첫 로컬 실습은 기존 `127.0.0.1` 바인딩을 사용하고 헤더 수신 타임아웃을 연기한다. **POST를 구현하거나 외부 접속을 허용하기 전에 헤더 수신 타임아웃을 추가한다.** 나중에 추가할 때는 읽을 때마다 갱신하는 대기 시간 대신 헤더 전체의 마감 시각을 관리한다. 기존 `poll()`의 100ms는 종료 플래그 확인 간격이다.

## 함수 계약과 호출 순서

```text
tcp_server_run → run_server → handle_http_client
                                ├─ receive_client_data
                                ├─ find_header_end
                                ├─ parse_http_request
                                └─ send_all
```

각 파일에서는 실행 진입점과 연결 처리 흐름을 먼저 배치하고 세부 함수는 아래에 둔다. 연결 루프는 수락·처리 호출·FD 정리를, HTTP 처리 함수는 수신·경계 확인·파싱·응답 선택을 순서대로 보여준다. 순수 파싱 함수는 TCP I/O와 독립된 작은 모듈에 둔다. 상태별로 전달만 하는 함수는 추가하지 않는다.

| 함수 | 입력 | 출력과 오류 계약 |
|---|---|---|
| `run_server(listen_fd)` | 열린 리스닝 FD | 클라이언트를 수락하고 처리 함수에 FD를 빌려준다. 반환 뒤 클라이언트 FD를 한 번 닫는다. 서버 수준 실패는 `tcp_server_run()`에 전달한다. |
| `handle_http_client(client_fd)` | 열린 클라이언트 FD | 16 KiB 누적 버퍼를 소유한다. 헤더를 받은 뒤 파서 결과로 응답을 선택하고 송신한다. 연결 처리 완료·클라이언트 오류·정상 종료 요청은 `0`, 서버 수준 실패는 `-1`을 반환한다. |
| `receive_client_data(client_fd, dst, capacity)` | 클라이언트 FD, 버퍼에서 다음에 쓸 위치, 남은 양수 용량 | `RecvResult`를 반환한다. `RECV_DATA`에서만 `bytes_read`가 양수다. EOF, 처리 중단, 서버 실패의 구분은 앞 절의 계약을 따른다. |
| `find_header_end(buffer, used)` | 지금까지 받은 전체 바이트와 길이 | 경계가 없으면 `0`, 있으면 첫 구분자 바로 뒤 오프셋을 반환한다. |
| `parse_http_request(buffer, header_end)` | 헤더 경계까지의 바이트와 길이 | `HttpParseResult` 구조체를 돌려준다. 성공 시 메서드, 요청 대상, 버전, 본문 프레이밍 분류를 담는다. 형식·필수 헤더·프레이밍 오류면 실패 상태를 반환한다. 응답 상태 코드는 호출자가 결정한다. |
| `send_all(client_fd, response, length)` | 클라이언트 FD, 고정 응답 바이트, 전송할 길이 | 기존 부분 송신 로직을 재사용한다. 모두 보내면 `1`, 클라이언트 소켓 오류나 종료 요청으로 중단하면 `0`, `poll()` 자체 오류면 `-1`을 반환한다. |

파서 결과의 메서드와 요청 대상은 **포인터와 길이로 된 읽기 전용 뷰**로 둔다. 버퍼를 소유하는 함수는 `handle_http_client()`다. 뷰는 버퍼가 살아 있고 해당 바이트를 변경하거나 덮어쓰지 않는 동안만 유효하다. 뷰를 직접 해제하거나 연결 처리 밖에 저장하지 않는다. 각 뷰를 비교할 때는 길이를 사용한다. 값 뒤에 널 문자가 붙어 있다는 가정은 없다.

`RECV_DATA`를 받으면 누적 길이를 늘리고 먼저 헤더 경계를 찾는다. 경계가 없고 버퍼가 가득 찼으면 `431`을 선택한다. 경계가 있으면 그 오프셋까지를 파서에 넘긴다. EOF나 중단 상태는 위의 수신 계약대로 처리한다. 응답은 한 번만 선택하고, 보낼 수 있으면 전송을 끝낸 뒤 호출자에게 돌아간다.

## 요청 본문과 응답 결정

파서는 헤더가 선언한 본문 프레이밍을 **본문 없음, 양수 `Content-Length`, `Transfer-Encoding` 사용**으로 구분한다. 이번에는 본문 길이를 소비하지 않으므로, `Content-Length` 값의 바깥쪽 공백을 제외하고 한 자리 이상의 10진수인지 확인하고, 0이 아닌 숫자가 있는지 본다. 길이를 정수로 변환할 때의 오버플로우를 이 단계에서 피할 수 있다. 중복이나 쉼표로 나열된 길이 값은 첫 실습의 엄격한 정책에 따라 거부한다.

`Transfer-Encoding`은 헤더의 존재만 확인하면 부족하다. 전송 코딩 목록의 문법과 순서를 검사한다. 여러 헤더 줄이 있다면 등장 순서대로 판단한다. 요청에서는 `chunked`가 한 번만, 마지막에 와야 한다. `chunked` 매개변수, 잘못된 목록 또는 `Content-Length`와 동시 사용은 오류로 처리한다. `Transfer-Encoding`이 없고 `Content-Length`도 없거나 0이면 본문이 없다. 헤더 뒤에 이미 읽은 바이트만으로 첫 요청의 본문이 있다고 판단하지 않는다.

| 조건 | HTTP 처리 함수가 선택할 결과 |
|---|---|
| 잘못된 요청 라인, 헤더, `Host` 또는 본문 프레이밍 | `400 Bad Request` |
| 문법상 유효한 전송 코딩 | 첫 실습에서는 디코딩을 지원하지 않으므로 `501 Not Implemented` |
| GET에 양수 `Content-Length`가 선언됨 | GET 본문을 처리하지 않는 첫 실습의 정책에 따라 `400 Bad Request` |
| 형식은 유효하나 지원하는 HTTP 메이저 버전이 다름 | `505 HTTP Version Not Supported` |
| HTTP/1.0 등 이번 실습에서 받지 않는 같은 메이저의 버전 | 첫 실습의 범위 밖으로 보고 응답 없이 닫는다. |
| 유효한 요청에 서버가 구현하지 않은 메서드가 지정됨 | `501 Not Implemented` |
| 본문 없는 유효한 GET의 요청 대상이 `/`가 아님 | `404 Not Found` |
| 본문 없는 정상 `GET / HTTP/1.1` | `200 OK`와 `Hello` 5바이트 |

요청 라인과 버전을 판별한 뒤 지원 대상 버전의 헤더를 검사한다. 헤더와 프레이밍 오류는 경로에 따른 응답보다 먼저 처리한다. 모든 고정 응답은 실제 본문 바이트 수에 맞춘 `Content-Length`와 `Connection: close`를 포함한다. 첫 실습은 HTTP/1.1의 제한된 부분을 확인한다. 최종 요구사항을 검토할 때는 `Date` 생성 등 이번 고정 응답에서 다루지 않은 항목도 확인한다.

## 구현 후 검증

| 확인할 것 | 검증 방법 | 통과 기준 |
|---|---|---|
| 정상 HTTP 응답 | `curl -i http://127.0.0.1:8080/` | `200 OK`, `Content-Length: 5`, `Connection: close`, 본문 `Hello`가 온다. |
| 나뉘어 도착한 헤더 | `GET / HTTP/1.1\r\nHost: localhost\r\n\r`을 보낸 뒤 대기하고 마지막 `\n`을 별도로 보낸다. | 마지막 `\n` 전에는 응답 바이트가 없고, 마지막 바이트를 보내면 정상 요청과 같은 응답이 온다. |
| 미완성 헤더에서 EOF | 위의 첫 조각만 보낸 뒤 클라이언트에서 `shutdown(SHUT_WR)`를 호출한다. | 서버가 EOF를 확인한 뒤 `400 Bad Request`를 보내고 연결을 닫는다. |
| 미완성 헤더에서 서버 종료 | 위의 첫 조각만 보내고 클라이언트의 송신 방향을 열어 둔 채 서버에 `SIGTERM`을 보낸다. | `400` 응답 없이 연결이 닫히고 서버가 정상 종료한다. |
| 헤더 크기 경계 | 정상 요청을 전체 16,384바이트로 맞춰 마지막에 구분자를 보낸다. 같은 크기에서 구분자가 끝나지 않은 경우도 보낸다. | 첫 요청은 `200`으로 처리되고, 두 번째 요청은 연결을 연 채 둬도 `431`로 응답한 뒤 닫힌다. |
| 경계 함수 자체 | 미완성 헤더, 완성 헤더, 완성 헤더 뒤에 데이터가 있는 버퍼를 전달한다. | 각각 `0`, 구분자 바로 뒤 오프셋, 뒤따르는 데이터의 시작 오프셋을 반환한다. |
| 요청 파서와 본문 판별 | 잘못된 요청 라인과 `Host`, `Content-Length`가 없거나 0인 요청, 잘못된 길이, 양수 길이, 전송 코딩이 선언된 요청을 비교한다. | 파싱과 응답 선택이 위 계약대로 이루어진다. 유효하지 않거나 처리 범위 밖인 본문을 성공 응답으로 처리하지 않는다. |
| 빈 연결과 경로 | 아무 요청 없이 송신을 끝내는 연결과, `/missing`에 대한 정상 GET 요청을 보낸다. | 빈 연결에는 응답이 없고, 정상 GET에는 `404`가 온다. |

구현은 학습자가 맡고, 각 검증의 기대 결과를 먼저 정한 뒤 실제 실행 결과와 비교한다.
