# TCP 소켓 서버 설계

## 서버의 역할

서버 시작 시 한 번 리스닝 소켓을 준비한다. 그다음 새 연결이 들어올 때마다 클라이언트 소켓을 받아 요청과 응답을 처리한다.

| 시점 | 호출 순서 | 결과 |
|---|---|---|
| 시작 시 한 번 | `socket()` → `bind()` → `listen()` | 연결을 받는 데 쓰는 `listen_fd` |
| 연결마다 | `accept(listen_fd, ...)` | 해당 클라이언트와 통신할 `client_fd` |
| 연결을 받은 뒤 | `recv(client_fd, ...)` → `send(client_fd, ...)` → `close(client_fd)` | 받은 바이트를 처리하고 연결을 정리 |

첫 실습은 연결을 하나씩 처리하며 받은 바이트를 그대로 보내는 TCP Echo 서버다. 대기는 시간 제한이 있는 `poll()`에 맡기고 소켓 호출은 논블로킹으로 수행한다. HTTP 파싱과 스레드 풀은 이후 단계에서 설계한다.

## 리스닝 소켓 준비 함수

- **함수.** `open_listener(port)` 안에서 `socket()`, `bind()`, `listen()`을 순서대로 호출한다.
- **입력.** 유효성 검사를 통과한 포트 번호. 예시는 `8080`이고, 로컬 테스트용 주소는 함수 안에서 `127.0.0.1`로 정한다.
- **성공.** `accept()`에 넘길 수 있는 FD를 반환한다. 반환 이후에는 호출자가 리스닝 FD를 관리한다.
- **실패.** 어느 호출에서 실패했는지 알리고 `-1`을 반환한다. 이미 생성한 FD가 있으면 준비 함수에서 닫는다.

세 호출을 한 함수로 묶으면 호출자가 준비 중간의 FD를 다루지 않고, 성공한 리스닝 FD만 받을 수 있다.

## 1단계 · `socket()`

첫 호출은 `socket(AF_INET, SOCK_STREAM, 0)`이다.

| 인자 | 의미 |
|---|---|
| `AF_INET` | IPv4 주소 체계 |
| `SOCK_STREAM` | 바이트 스트림 소켓 |
| `0` | 이 조합에 맞는 기본 프로토콜인 TCP 선택 |

성공하면 유효한 FD가 반환된다. 예를 들어 `3`이면 코드가 그 번호로 운영체제의 소켓을 참조한다. 실패하면 `-1`을 반환하며 정리할 FD는 없다. 이 단계의 검증 기준은 **유효한 FD를 얻었는지**다.

`3`은 코드가 소켓을 참조하는 번호이고, `8080`은 클라이언트가 접속할 포트다. 준비 함수는 포트를 보관했다가 `bind()`에 FD와 `127.0.0.1:8080` 주소를 전달한다. `nc`로 접속하는 테스트는 `listen()`까지 완료한 뒤 수행한다.

## 2단계 · `bind()`로 로컬 주소 지정

첫 버전부터 빠른 재시작을 고려해 `bind()` 전에 `SO_REUSEADDR`를 켜기로 했다. 준비 순서는 `socket()` → `setsockopt()` → `bind()` → `listen()`이다.

1. `socket()`에서 얻은 FD에 `setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &enabled, sizeof(enabled))`를 호출한다. `enabled`는 값이 `1`인 `int`다.
2. IPv4 주소 구조체인 `struct sockaddr_in`에 `AF_INET`, `htons(port)`, `127.0.0.1`을 넣는다.
3. `bind(fd, (const struct sockaddr *)&addr, sizeof(addr))`를 호출한다. 예를 들어 포트가 `8080`이면 해당 FD에 `127.0.0.1:8080`을 지정한다.
4. `bind()`가 `0`을 반환하면 같은 FD를 `listen()`에 넘긴다. `setsockopt()`나 `bind()`에서 `-1`이 돌아오면 실패한 호출과 오류를 알리고 FD를 닫은 뒤 `-1`을 반환한다.

다른 서버가 같은 주소와 포트에서 이미 연결을 받고 있으면 `SO_REUSEADDR`를 켜도 바인딩은 실패할 수 있다. 이 경우 `EADDRINUSE`를 확인한다. 이 단계의 검증 기준은 사용 가능한 주소와 포트에서는 바인딩이 성공하고, 이미 점유한 주소와 포트에서는 실패를 알리고 FD를 정리하는 것이다.

## 3단계 · `listen()`으로 연결 대기 시작

`bind()`가 성공하면 같은 FD로 `listen(fd, 16)`을 호출한다. `backlog`는 `accept()`가 연결을 꺼내기 전까지 대기열에 둘 수 있는 연결 수를 운영체제에 요청하는 값이다. 실제 대기열 한도는 운영체제에 따라 달라질 수 있다. 동시 요청 처리 수는 워커 수와 처리 방식에 따라 결정된다.

첫 버전의 `backlog`는 `16`으로 정했다. 같은 Mac에서 `nc`로 연결 한두 개를 붙여 흐름을 확인하는 데 충분하다. 동시 접속 실험에서 대기열이 자주 찬다는 근거가 생기면 값을 다시 검토한다.

- **성공.** `listen()`이 `0`을 반환하면 `open_listener()`는 기존 FD를 호출자에게 돌려준다. 호출자는 그 FD를 `listen_fd`로 받아 `accept()`에 사용한다.
- **실패.** `listen()`이 `-1`을 반환하면 실패 원인을 알리고 FD를 닫은 뒤 `open_listener()`도 `-1`을 반환한다.

이 단계까지 구현하면 `nc 127.0.0.1 8080`으로 TCP 연결이 맺어지는지 확인할 수 있다. 서버 코드가 그 연결을 꺼내 데이터를 읽고 쓰는 동작은 다음 단계에서 검증한다.

## 4단계 · `accept()`로 연결과 상대 주소 받기

첫 버전부터 클라이언트 FD와 상대 IPv4 주소 및 포트를 받아 접속 로그에 남긴다. 같은 서버 포트에 접속한 클라이언트들의 상대 포트가 어떻게 다른지 직접 확인하기 위해 이 방식을 선택했다.

1. `struct sockaddr_in peer`에 상대 주소를 받을 공간을 마련한다. `socklen_t peer_len`은 호출 전에 `sizeof(peer)`로 초기화한다.
2. `accept(listen_fd, (struct sockaddr *)&peer, &peer_len)`을 호출한다. 리스닝 FD가 읽기 준비 상태일 때 호출한다. 대기 중인 연결이 없으면 논블로킹 모드에서 `EAGAIN` 또는 `EWOULDBLOCK`이 반환될 수 있다.
3. 성공하면 새 `client_fd`로 통신하고, `inet_ntop()`로 변환한 상대 IP와 `ntohs()`로 변환한 상대 포트를 접속 로그에 남긴다. 새 연결을 받는 데는 계속 `listen_fd`를 사용한다.
4. 실패로 `-1`을 받으면 해당 호출에서 정리할 클라이언트 FD는 없다. `errno`를 확인해 다음과 같이 처리한다.

| `accept()` 오류 | 처리 |
|---|---|
| `EINTR` | 종료 요청을 확인하고, 계속 실행 중이면 같은 `listen_fd`로 다시 기다린다. |
| `ECONNABORTED` | 수락하려던 연결이 중단됐다. 계속 실행 중이면 같은 `listen_fd`로 다음 연결을 기다린다. |
| `EAGAIN` 또는 `EWOULDBLOCK` | 즉시 수락할 연결이 없다. `poll()`로 돌아간다. |
| 그 외 | 오류를 기록하고 리스닝 FD를 닫은 뒤 서버를 종료한다. |

수락하려던 연결 하나가 취소돼도 다음 클라이언트를 받을 수 있도록 `ECONNABORTED`를 재시도 대상에 포함했다. 종료 요청을 확인한 경우에는 `EINTR`이어도 다시 기다리지 않는다.

같은 Mac에서 `nc`를 두 개 실행해 서버의 `8080`번 포트로 접속한다. 서버가 받은 각 연결의 로그에 `127.0.0.1`과 서로 다른 클라이언트 포트가 나타나는지 확인한다.

## 5단계 · `recv()`와 `send()`로 Echo 응답 보내기

`accept()`로 받은 `client_fd`에서 `recv(client_fd, buffer, sizeof(buffer), 0)`을 호출한다. 첫 실습에서는 수신한 바이트를 그대로 같은 연결에 돌려준다.

| `recv()` 반환값 | 처리 |
|---|---|
| 양수 | 버퍼 앞에서 반환값만큼의 바이트를 읽었다. 그 바이트를 `send()`로 돌려준다. |
| `0` | 상대가 송신을 끝냈다. Echo 처리를 마치고 `client_fd`를 닫는다. |
| `-1`과 `errno == EINTR` | 종료 요청을 확인한다. 계속 실행 중이면 같은 `client_fd`로 다시 읽는다. |
| `-1`과 `EAGAIN` 또는 `EWOULDBLOCK` | `poll()`로 돌아가 해당 FD에서 읽을 수 있을 때까지 기다린다. |
| `-1`과 그 외 오류 | 오류를 기록하고 해당 `client_fd`를 닫는다. |

TCP에서 `hello`는 한 번에 읽힐 수도 있고 `he`와 `llo`로 나뉘어 읽힐 수도 있다. `send()`도 요청한 바이트 중 일부만 보낼 수 있으므로, Echo할 때는 반환값으로 보낸 위치를 추적한다.

시그널로 일시 중단된 수신은 종료 요청을 확인한 뒤 이어간다. 일시적으로 읽을 수 없으면 `poll()`에서 다시 기다리고, `ECONNRESET` 같은 연결 오류가 발생하면 해당 연결을 끝낸다.

### 확정 · 연결에서 Echo를 반복

B를 선택했다. `recv()`가 데이터를 읽으면 같은 연결에 받은 바이트를 돌려주고 다시 읽는다. 예를 들어 `he`와 `llo`를 따로 읽어도 두 부분을 차례대로 돌려준다. `recv()`가 `0`을 반환하면 상대가 송신을 끝냈으므로 연결을 정리한다.

같은 연결에서 여러 번 나눠 보낸 데이터도 모두 Echo할 수 있다. 상대가 연결을 열어 둔 채 더 보내지 않으면 서버는 `poll()`에서 그 클라이언트의 데이터를 기다린다. 연결을 하나씩 처리하는 첫 버전에서는 이 대기 때문에 다음 클라이언트의 처리가 늦어질 수 있다.

### 확정 · 부분 전송 이어 보내기

`recv()`가 양수 `received`를 반환하면 `sent = 0`에서 시작한다. `sent < received`인 동안 `send()`에 시작 위치 `buffer + sent`와 남은 길이 `received - sent`를 넘긴다. 양수가 돌아오면 그 값만큼 `sent`를 늘린다. `sent == received`가 되면 다음 `recv()`로 넘어간다.

예를 들어 `hello` 5바이트를 읽은 뒤 첫 `send()`가 2를 반환하면, 다음 호출에는 `buffer + 2`부터 남은 3바이트를 넘긴다. 이렇게 하면 부분 전송이 반복돼도 보낸 바이트의 위치를 유지할 수 있다.

### 확정 · 송신 오류 처리

남은 바이트가 있을 때는 `send()`의 반환값에 따라 처리한다.

| 반환값 | 처리 |
|---|---|
| 양수 | 반환된 길이만큼 `sent`를 늘리고 남은 바이트를 이어 보낸다. |
| `-1`과 `errno == EINTR` | 종료 요청을 확인한다. 계속 실행 중이면 `sent`를 유지한 채 같은 위치와 길이로 다시 호출한다. |
| `-1`과 `EAGAIN` 또는 `EWOULDBLOCK` | `sent`를 유지하고 `poll()`로 돌아가 쓰기 준비를 기다린다. |
| `-1`과 그 외 오류 | 오류를 기록하고 해당 클라이언트 연결을 정리한다. |
| `0` | 진행이 없으므로 반복을 중단하고 해당 클라이언트 연결을 정리한다. |

`EINTR`과 일시적인 쓰기 대기 상태는 위 규칙으로 처리한다. 다른 오류나 진행 없는 반환에서는 반복을 끝낸다.

### 확정 · 시작 시 `SIGPIPE` 무시

서버 시작 시 `sigaction()`으로 `SIGPIPE`의 동작을 `SIG_IGN`으로 설정한다. 끊긴 소켓에 쓰다가 `SIGPIPE`의 기본 동작으로 서버 프로세스가 종료되는 상황을 막기 위해서다.

이 설정은 프로세스 전체에 적용된다. `send()`가 `-1`을 반환하고 `errno`가 `EPIPE`이면, 확정한 송신 오류 정책에 따라 오류를 기록하고 해당 연결을 닫는다. 서버는 새 연결을 계속 받을 수 있다. 이 POSIX 방식은 macOS와 Linux에서 사용하며, 이후 리버스 프록시가 백엔드 소켓에 쓸 때도 적용된다.

## 6단계 · 종료 요청을 확인하는 대기 방식

A를 선택했다. `SIGINT`·`SIGTERM` 핸들러는 종료 플래그만 설정한다. 정리 작업은 서버의 실행 흐름에서 맡는다. 시간 제한이 있는 `poll()`에서 돌아올 때마다 플래그를 확인한다. 종료 요청을 확인한 뒤에는 새 연결을 받기 위한 대기로 돌아가지 않는다.

리스닝 소켓과 받아들인 클라이언트 소켓에는 논블로킹 모드를 적용한다. 새 연결을 받을 때는 리스닝 FD의 읽기 준비를, 클라이언트를 처리할 때는 그 FD의 읽기 또는 쓰기 준비를 `poll()`로 기다린다. `accept()`·`recv()`·`send()`가 `EAGAIN` 또는 `EWOULDBLOCK`으로 돌아오면 다시 대기한다. `poll()`이 `EINTR`로 중단돼도 플래그를 확인한다.

별도 파이프 없이 종료 요청을 확인할 수 있어 첫 실습에 이 방식을 선택했다. 유휴 상태에서도 대기 시간이 끝나면 깨어난다. 종료 검증은 접속자가 없을 때와, 접속자는 있지만 데이터를 보내지 않을 때 각각 `Ctrl+C`를 눌러 수행한다.

[POSIX poll()](https://pubs.opengroup.org/onlinepubs/9799919799.2024edition/functions/poll.html)

### 확정 · 종료 요청을 확인하면 열린 소켓 닫기

첫 Echo 버전에서는 A를 선택했다. 서버 실행 흐름에서 종료 플래그를 확인하면 새 연결 수락과 현재 연결의 송수신을 중단한다. 열린 `client_fd`가 있으면 해당 FD를 닫고, 리스닝 FD도 닫은 뒤 종료한다.

예를 들어 `hello` 중 `he`를 보낸 뒤 종료 요청을 확인했다면, 아직 보내지 않은 `llo`의 전송을 재개하지 않는다. 상대는 응답 일부만 받을 수 있다. 첫 버전에서는 상대가 응답을 읽기를 기다리는 대신 열린 소켓을 정리하고 종료하는 흐름을 검증한다.

### 확정 · `poll()` 대기 시간 100ms

첫 버전은 `poll()`을 한 번 호출할 때 최대 100ms를 기다리도록 요청한다. 연결이나 데이터가 준비되면 대기 시간 안에도 반환할 수 있다. 이벤트 없이 시간이 끝나면 종료 플래그를 확인하고, 계속 실행 중이면 같은 소켓에서 다시 기다린다.

같은 Mac에서 TCP Echo를 시험하는 동안 유휴 대기에서 주기적으로 돌아와 종료 요청을 확인할 수 있도록 100ms를 선택했다. 이 값은 종료 확인을 위한 대기 간격이다. 입력이 없는 클라이언트 연결은 이 시간만으로 종료하지 않는다.

## 7단계 · `poll()` 결과 처리

서버는 기다리는 작업에 따라 FD 하나를 감시한다. 새 연결 수락 또는 클라이언트 수신을 기다릴 때는 `POLLIN`, 남은 Echo 바이트를 보낼 때는 `POLLOUT`을 요청한다. 쓰기 감시는 보낼 바이트가 있을 때만 한다.

- `poll()`은 반환 직후 종료 플래그부터 확인한다. 설정돼 있으면 열린 FD를 정리하고 종료한다.
- 반환값이 `0`이면 100ms 대기가 만료된 것이므로 같은 작업을 다시 기다린다.
- 반환값이 `-1`이고 `errno == EINTR`이면, 종료 플래그를 확인한 뒤 계속 실행 중일 때만 다시 기다린다. 다른 `poll()` 호출 오류는 원인을 기록하고 서버를 종료한다.
- 양수가 돌아오면 해당 FD의 `revents`에서 다음 표시를 확인한다.

| `revents` | 처리 |
|---|---|
| `POLLNVAL` | 사용할 수 없는 FD로 판단하고 기록한다. 클라이언트 FD이면 해당 연결 처리를 끝내고, 리스닝 FD이면 서버를 종료한다. |
| `POLLERR` | 소켓 오류를 기록한다. 클라이언트 쪽이면 해당 연결을 정리하고, 리스닝 쪽이면 서버를 종료한다. |
| 클라이언트 수신 중 `POLLIN`과 `POLLHUP`이 함께 옴 | 사용자가 고른 B에 따라 `recv()`로 남은 데이터를 먼저 읽는다. 읽은 데이터에는 기존 Echo 규칙을 적용한다. EOF 또는 오류가 확인되면 해당 연결을 정리한다. 끊김 표시가 함께 온 호출에서 `recv()`도 당장 읽을 것이 없다고 반환하면 연결을 정리한다. |
| 클라이언트에서 `POLLHUP`만 옴 | 해당 연결을 정리한다. 쓰기를 기다리는 동안 끊김이 확인된 경우에도 남은 전송을 중단한다. |
| 리스닝 FD에서 `POLLHUP` | 리스닝 소켓을 더 사용할 수 없는 상태로 처리하고 서버를 종료한다. |
| 요청한 준비 이벤트 | 리스닝 소켓은 `accept()`, 클라이언트는 현재 단계에 맞춰 `recv()` 또는 `send()`를 호출한다. |

클라이언트의 수신 버퍼는 4096바이트로 시작한다. Echo는 `recv()`가 반환한 길이로 처리하므로, 버퍼보다 긴 입력은 여러 번에 나누어 같은 순서로 돌아간다.

## 8단계 · 실행 인자와 시작 순서

`./tiny-web-server <port>` 형식으로 실행한다. `8080`은 테스트 예시다. 인자는 하나만 받으며, 10진수 숫자로만 이루어진 `1`~`65535`를 포트로 허용한다. 인자가 빠졌거나 추가됐거나 범위를 벗어나면 사용법과 오류를 표준 오류에 출력하고 실패 상태로 종료한다. 포트 검증은 `open_listener(port)`에 전달하기 전에 한다.

시작 순서는 **포트 검증 → 시그널 등록 → 리스닝 FD 준비 → 연결 루프**다. `SIGPIPE`는 `SIG_IGN`으로 등록한다. `SIGINT`와 `SIGTERM`은 공통 종료 플래그인 `volatile sig_atomic_t`에 표시하는 핸들러를 등록한다. 시그널 등록에 실패하면 소켓을 열기 전에 오류를 알리고 실패 상태로 종료한다.

리스닝 FD와 `accept()`가 돌려준 클라이언트 FD에는 각각 `fcntl()`로 기존 플래그를 유지하면서 `O_NONBLOCK`을 추가한다. 리스닝 FD는 연결 루프에 전달하기 전, 클라이언트 FD는 첫 송수신 전에 설정한다. IPv4 주소는 계속 `127.0.0.1`을 사용한다.

## 9단계 · FD 소유권과 정리

| 상황 | 정리 책임 |
|---|---|
| 리스닝 FD 준비 도중 실패 | `open_listener()`가 생성한 FD를 닫고 실패를 반환한다. |
| 리스닝 FD 준비 완료 | 메인 흐름이 리스닝 FD를 소유하고, 서버가 끝날 때 닫는다. |
| 클라이언트의 논블로킹 설정 실패 | 방금 받은 클라이언트 FD를 닫고 오류를 기록한다. 계속 실행 중이면 다음 연결을 받는다. |
| 클라이언트 EOF 또는 연결 오류 | 클라이언트 처리 흐름이 해당 FD를 닫는다. 계속 실행 중이면 메인 흐름이 다음 연결을 받는다. |
| 종료 요청 | 새 수락과 송수신을 중단하고, 열린 클라이언트 FD와 리스닝 FD를 각 소유자가 정리한다. 준비 과정에서 종료 요청을 확인하면 연결 루프에 진입하지 않는다. |

FD는 소유한 쪽에서 한 번만 정리한다. 클라이언트 오류는 그 연결의 종료로, 리스닝 또는 `poll()` 자체 오류는 서버의 실패 종료로 처리한다. 신호에 따른 정상 종료는 열린 FD를 정리한 뒤 성공 상태를 반환한다.

## 구현 완료 기준

| 검증 상황 | 기대 결과 |
|---|---|
| 유효한 포트로 빌드 후 실행 | `nc 127.0.0.1 8080`으로 접속할 수 있고, 상대 IP와 포트가 로그에 찍힌다. |
| 같은 연결에 여러 입력과 버퍼보다 긴 입력 전송 | 받은 바이트를 빠짐없이 같은 순서로 돌려준다. 부분 전송은 남은 위치에서 이어진다. |
| 마지막 데이터를 보내고 송신을 종료 | 상대가 읽을 수 있다면 마지막 바이트까지 Echo하고 EOF에서 해당 연결을 정리한다. |
| 클라이언트가 갑자기 끊김 | 서버 프로세스가 살아 있고 다음 클라이언트가 Echo를 받을 수 있다. |
| 잘못된 포트 또는 점유 중인 포트 | 원인을 표시하고 실패 상태로 종료한다. |
| 접속 대기 중, 유휴 클라이언트 연결 중 또는 송신 대기 중 종료 신호 | `SIGINT`와 `SIGTERM` 모두에서 새 요청을 받지 않고 열린 FD를 정리한다. 남은 Echo 전송은 기다리지 않는다. |

이 기준은 TCP Echo 첫 버전에 적용한다. HTTP 파싱, 정적 파일, 리버스 프록시, 스레드 풀은 뒤 단계에서 설계한다.
